# Natural wiki trial design

This is one synthetic, bounded workflow trial, separate from earlier historical-import attempts and from external-acquisition metrics. The business task is to create a new PRIVATE structured workspace, install the exact supplied f828 Wiki package by its public compiled material, and ensure one exact welcome note exists. The actor must follow the frozen c5e entry and installed CLI. No new SDK build is involved.

The selected package is `/protocols/wiki` from f828 commit `f828b6c50a0a58d1e718af90f653b214adcc3328`. Its raw source digest and compiled protocol digest are different fields: source digest `05300473589495f96080b96c78962acc0c0ecc8bf1ae82d84f214042a6d30ca2`, output protocol digest `33f799e4b168b28032348a26e8c5d320cb2c43550e3effc60f584dc4561717a3`. The protocol digests are the same canonical digest domain; compilation sorts the action list. The task requires installing the supplied package and selecting its newly installed instance. The built-in instance is not a substitute.

Setup is expected to verify the immutable c5e artifact/source guards and f828 source tree, create a fresh 0700 task root, copy only the selected Wiki package files, generate a fresh Owner PEM, and leave the configured native `state_dir` absent. A pinned public TypeScript author path parses the supplied package, creates its exact dependency closure, and compiles the closure for comparison. It writes only the closure and public digest metadata needed by the direct native install input. The setup must not create a workspace, identity state, or Owner database.

The task uses public native Owner operations: selected-PEM import into the configured absent identity path; identity info; `owner-create` for a new private structured workspace; direct install of the supplied closure with the signed owner actor granted the Wiki `EDITOR` role and `EDIT` capability; continuation until installed; and signed Owner read to select the new instance by entrypoint and compiled protocol digest. It then inspects the signed read before creating the note. If the action outcome is uncertain, it must inspect and recover the saved action and verify the signed read before deciding whether another submission is needed.

The local fixture is planned to drop exactly one successful HTTP response to a `wiki.create` commit after the reference service accepts it. It should capture only command/action/workspace IDs, response class, and counters in protected operator evidence; it must not retain the raw body, note contents, PEM, or keys. The actor receives no knowledge of the injected response loss. The acceptance oracle will score observed entry/protocol use, identity selection/import, source/package selection, recovery, final signed read, and timely completion/handoff separately from the note's business result. If the client transparently reconciles the lost response, record that actual path and do not demand a particular error or retry call.

No fixture/service has been started and no actor has been launched on this checkpoint. Root approval is required after core source review and setup-ready evidence before the one 480-second capture.
