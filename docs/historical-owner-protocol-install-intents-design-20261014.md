# Historical Owner protocol-install intent migration

This is the next source-family port gap after accepted package-stage migration. `parse_legacy_source` currently rejects every nonempty `protocol_install_intents` map. In pinned f828 `workspace-secure-agent.ts`, `installProtocol` stores an `intentHash` at `${workspaceId}.${instanceId}` before calling `post` for `secure.structure.begin`; `post` separately persists the exact `{path,body}` packet in `pending[commandId]` before network, then removes that packet after success. The map remains until `installProtocol` verifies the installed source, completes any `secure.structure.page/end` work through `upgradeStructure`, and clears it. The map value hashes the resolved semantic install request (normalized manifest, grants, composition, disclosure, checkpoint and package source when present), not raw JSON options, a signed packet, or a command ID. The f828 source and its existing install-intent tests show applied-response-loss, pre-send, same-options retry, retained grant/checkpoint conflicts, and BEGIN/PAGE/END continuation. Native must not treat a hash-only map as a retryable signed request.

The first genuine fixture will use the current public `SecureAgentClient.installProtocol` and a valid source-backed manifest on a task-local PRIVATE Owner. It will capture three distinct states without editing legacy files or service DB: (1) a `secure.structure.begin` applied with the response dropped, leaving map plus exact saved pending BEGIN packet; (2) an intercepted pre-send BEGIN after `post` saves pending, leaving the same map+packet shape but no signed BEGIN; (3) a completed installation whose final `post` succeeds and saves pending removal, then a test wrapper throws before `installProtocol` can re-enter and clear the map, leaving map/no pending and complete signed ACTIVE installation. It will assert the map key/value, pending command/path/body/commit hash where present, current signed sequence/policy/installation, and read-only service effect count. Marker-only immediately after the map save but before `post` saves pending is another possible orphan state; it cannot be classified as completed from local absence and requires a separate explicit material-bound replan.

The migration contract requires a caller-selected workspace and complete source snapshot digest, explicit install-intent key/options identity, protected PEM/state/checked SQLite backup, and source quiescence. Before PREPARED, native must verify current Owner/key/ring and the complete origin-bound replay, bind the map hash to caller-supplied canonical original options/resolved source, and classify the selected exact packet against signed history. A completed map/no-packet case may be acknowledged only after proving the full signed BEGIN/PAGE/END ancestry and installed protocol/instance at the selected source, plus current Owner authority; later authenticated history is allowed only when those historical proofs remain complete. A saved pending BEGIN/PAGE/END packet remains exact and protected; ordinary attach/read must not POST it. An explicit per-ID recovery first reconciles exact signed command/commit. If absent, POST is allowed only at its signed predecessor under current policy/Owner, with the original packet/ID and fresh per-attempt read proof, followed by fresh signed replay. Later head, changed policy/epoch, wire ENFORCE, HTTP rejection, or missing original packet remains retained unresolved without an accepted/rejected inference or regenerated signature. The attachment remains restricted until full signed install completion or an explicit safe disposition; unrelated local intents stay preserved and unsubmitted.

Crash order is material: the map may exist before any packet, a pending packet may exist before network, and a successful POST may remove pending before the caller cleans the map. Protected plan/attach history must be durable before native POST, retain exact packet and options/material inputs, and resume after all original source files are removed using protected copies plus fresh replay. A bounded first positive can classify the genuine completed map and the two saved-BEGIN states; this does not close PAGE/END recovery or hash-only orphan replan. The subsequent recovery gate must cover those states rather than treating refusal as completion. The fixture setup pass is recorded separately; no native product allowance, installed facade, or natural Agent workflow result follows from it.

The genuine fixture at `7c931f9` establishes the wire shape for the first implementation slice: `protocol_install_intents` contains one `${workspaceId}.${instanceId}` key and resolved semantic hash. BEGIN pending has one `pending[commandId]` entry with a canonical `{commit,policy_update}` body; its signed action is `secure.structure.begin`, sequence is the selected source sequence plus one, and the pending map key equals `commit.payload.command_id`. The applied-loss source has that exact command at signed sequence 2 and structure SEEDING; the pre-send source remains at signed sequence 1 and ACTIVE. Completed END has no pending packet, signed sequence 3 and ACTIVE installed instance. Native must match pending packet hash and command to the complete authenticated replay; it must not treat the optional local map as signed evidence. Additional workspace map entries remain preserved in the checked backup and are never implicitly submitted.

The selected direct-BEGIN inventory at `b52dfc3` is deliberately read-only and singleton-only. It accepts exactly one `${workspace}.${instance}` map entry and exactly one pending `secure.structure.begin` packet, checks its resolved four-key options and complete closure material against the original signed request, and reports the full TS-state digest and signed-replay classification. Ordinary attach still invokes the default parser, which refuses the map. This is an intermediate source proof, not migration support for other map entries or a durable handoff.

The next durable direct-BEGIN path needs its own attach-bound installation provenance. The selected command, instance, map hash, source digest, original request/commit hash, options and complete bounded material must be protected before any native POST. A manifest-last owned plan will copy the independently checked TS state, PEM and SQLite snapshot plus material/options; the recovery lock spans final source recheck and PREPARED. After PREPARED, an imported direct `InstallRow` must carry `import_attach_id` and remain invisible to ordinary install listing/continuation. Only the matching attach recovery API can reconcile the original packet and drive later work. Reopen must validate the plan, source identity, selected map entry, exact packet and replay again from protected copies; no original source file is required after durable consent.

The existing generic `SecurePrivatePackageInstall::continue_install_json_with_cancel` cannot simply consume an imported applied BEGIN row: it pins its `prior` replay to the current head and requires a direct row's source checkpoint to equal that current checkpoint. For an already applied saved BEGIN, the original source predecessor is sequence 1 while current replay is sequence 2. A crate-private, attachment-bound historical-source context should feed the existing PAGE/END planning and saved-step engine; ordinary public continue keeps its current-checkpoint guard. That dedicated recovery entrypoint must verify the original BEGIN against the historical signed predecessor, reconcile it against complete signed replay with zero POST when applied, and use the original exact request only if current head/policy still equals that predecessor. PAGE/END steps may then be authored only from the verified original install snapshot and fresh current SEEDING head under current Owner/keyring authority, with each new ID and request saved before POST. Result-loss recovery reuses the saved step, and ACTIVE installed instance/protocol readback is the unlock boundary. Generic install and Owner action/format selectors remain restricted until that proof. A later unrelated head or policy change before original BEGIN recovery is an unresolved packet, never a reason to re-sign, infer rejection or submit at a new head.

For this first importer, the selected options object has exactly `instance_id`, `entrypoint`, `manifest`, and `grants`; optional composition, disclosure, expected checkpoint and package-source/object-source forms stay fail-closed until their own verifiers are wired. The plan manifest must bind the final attach ID and future InstallRow command ID before PREPARED, plus workspace/Owner/instance, selected `${workspace}.${instance}` map key/hash, all three inspected source digests, canonical saved `{commit,policy_update}` and request path, original signed commit hash, and historical predecessor/policy/epoch. The old client stores a request body object rather than original HTTP serialization bytes: native preserves the signed packet and its canonical request envelope, while a retry may create a fresh transport read proof. A random protected staging directory and manifest-last publish prevent a partial copy from being adopted; only owner-marked unreferenced residue may be cleaned under the root lock. Resume revalidates every copied byte and binding against signed replay before any effect.
