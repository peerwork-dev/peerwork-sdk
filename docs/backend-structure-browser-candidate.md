# Browser access

Use the canonical `/workspaces/WORKSPACE_ID` URL, or a link generated by
`peerwork_url`. A PRIVATE link includes `?access=private`. The earlier
`/private/workspaces/…` routes redirect to the canonical route; they do not
restore retired APIs. The historical filename is retained for existing links.

Native Peers use [the current tools](agent-tools.md) and
[connection guide](participant-connect.md). Browser access uses the advertised
`backend-structure-v1` contract, not the retired delegated browser login.

## Approve the intended browser

The browser owns its signing and recipient keys. It displays one signed access
request for an already authorized Owner Peer to approve. Check the intended
Workspace, service, device and requested action; receiving a request does not
itself authorize approval. Keep the Owner identity in its original client.

Describe `access.approve` through `peerwork_manage`, then invoke it with the
exact browser request and one stable operation ID:

```json
{"mode":"invoke","operation":"access.approve","workspace":"project","operation_id":"approve-this-browser-request","body":{"request_jws":"EXACT_SIGNED_BROWSER_REQUEST"}}
```

The engine verifies the request, signs the approval and encrypts authorized
content keys for that browser. Return the verified
`result.browser_approval_reference` to the intended user. Paste it into
**Owner approval reference**, then select **Connect this browser**. A pending
approval resumes with its original `recovery_arguments`; do not create a new
client or manually construct a signature.

The reference identifies the exact Workspace, browser request, Owner, accepted
command and intent digest. It is not a bearer credential. The browser verifies
the matching request, Owner signature and signed content-key epoch floor before
opening content. The API response cannot choose a new trusted Owner on its own.

## Personal and shared computers

Persistent personal-browser access is a release candidate. It requires the
`persistent-browser-access-v1` discovery feature and native SDK0.3.21 or later. Older0.3.20 binaries do not support it. See the
[versioned persistent-access contract](persistent-browser-access.md).

When that feature is available, **Personal browser** is selected by default.
The request explicitly asks to stay connected until access is ended or revoked.
Approve that exact v2 request without adding `ttl_ms`: the SDK selects its
persistent authorization and follows future current keys when body access is
granted. Normal visits reuse the device and membership; no recurring approval
or login-renewal write is required.

Uncheck **Personal browser** on a shared computer. The browser then requests
finite v1 access and recommends12hours. For a finite request, the Owner supplies
`ttl_ms` explicitly; without it the native finite-session default remains24hours,
with a31-day maximum capped by the recipient certificate. Existing finite
approvals retain their original expiry. They never become indefinite silently.

Signed enrollment requests remain valid for10minutes. Each signed command also
has a maximum10-minute freshness window. Both use signed service time; changing
the browser clock does not change authority. These windows are independent of
how long a personal browser remains admitted.

## Read, chat and selected business actions

A browser is a separate ordinary Space member, not the approving Peer. Baseline
communication and current member visibility follow the Workspace policy.
Business roles and selected write actions remain explicit grants; browser
approval does not copy the Owner's responsibilities or grant administration.

The main room, task threads and selected record pages use indexed bounded reads.
The browser verifies fresh service receipts and original author signatures.
It does not download the journal or reconstruct the business state from history.
Readable structure has `BACKEND_CURRENT_STATE` assurance; an opened private body
has author-signature and AEAD assurance. Neither is an independent proof that a
model read or answered a message.

An ordinary private-body approval supplies the current key. Following future
current keys and retained historical access are separate signed permissions.
The Owner coordinator seals keys for the exact browser recipient; the service
never obtains body keys. Missing historical keys produce an explicit body state,
not an empty Workspace. See [key lifecycle](backend-structure-content-keys-candidate.md).

Device keys are non-extractable CryptoKeys in IndexedDB, scoped by service and
Workspace. Plaintext bodies are not saved in the pending request journal.
Bodies support up to64KiB per action in total.

## Recover a request or end access

A write is encrypted and saved before submission. Reply loss is reconciled by
the original command and business-intent digest. Resume the exact pending
operation rather than changing its ID or silently rebasing a revision.

The persistent-access candidate makes **End browser access** independent of an
earlier pending write. It saves a local end marker and locks other tabs before
contacting the service. Offline ending is shown as locally locked with server
revocation pending. Reconnection retries the same end intent; it does not erase
keys or the earlier business request.

The end command can revoke only that device's exact membership generation.
After a new enrollment, an old signed write cannot act as the new generation.
A verified original commit is reconciled normally. A signed absence result plus
an obsolete signed generation allows the old encrypted packet and evidence to
be archived locally, freeing the pending slot for a new deliberate action.
An unknown outcome stays pending. The bounded recovery archive retains the last32
such resolutions; it is not the canonical server conversation history.

Ending access fences subsequent encrypted writes until ordinary Owner-side key
rotation. Already obtained keys and plaintext cannot be erased retroactively.

## Hosting and compatibility

The frontend may run as `WORKSPACE_ROLE=public` with a configured
`WORKSPACE_CONTROL_ORIGIN` and no database or service signing key. Set Control's
`WORKSPACE_PUBLIC_ORIGIN` to the exact frontend origin for CORS. Deploy matching
browser assets and service capabilities. The frontend health check rejects a
missing entry asset.

Update native readers before using the persistent candidate: older binaries fail
closed on its new versioned proofs. An SDK update alone does not extend an old
finite grant. No identity migration or history replay is required.
