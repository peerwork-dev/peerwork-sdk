# Pending historical package-stage migration contract

This contract began as a design checkpoint. The one-part saved-packet runtime gate is recorded separately in `historical-owner-pending-package-stage-20261013.md`. The accepted completed-marker importer handles a signed, completed one-part stage whose old client has no matching pending packet.

The old f828 client saves `package_stage_intents` before invoking `post()`. `post()` then saves `pending[command_id] = {path, body:{commit}}` before making the HTTP request. These writes yield three distinct states: a marker with no packet and no signed stage (orphan before pending save), a marker plus packet without a signed stage (saved before send), and a marker plus packet with a signed stage (applied response lost). A marker with no pending packet can be accepted only if complete authenticated replay proves the exact command and full package part, as in the existing completed path. An orphan must remain unresolved; it cannot be silently cleared or treated as proof of nonapplication.

Before a new immutable attachment row, expose a no-POST inventory of the authenticated local stage marker and exact saved pending command. The implemented one-part inventory returns command/source IDs, source hash/sequence, a replay-derived local status, and SHA-256 of the entire protected TS agent-state file. The caller selects the exact command ID and that state-file digest; the importer compares both before PREPARED. Owner PEM and the complete canonical SQLite intent snapshot are hashed and rechecked separately by the importer and pinned in its protected attachment row. The inventory digest is not a combined fingerprint of all three files. No ordinary inspection, listing or attach submits anything; unrelated pending work remains preserved and unsubmitted.

The selected packet's original signed commit, ciphertext, command ID and signed context are immutable. The f828 state stores a body object, not historical HTTP bytes. Native storage therefore journals a canonical `{commit:...}` retry envelope with its digest; it does not claim that reconstructed HTTP serialization is the original. The current secure-commit POST route authenticates the signed commit body and does not require the additional X-Peerwork-Read header sent by the old client; that header, where used, is per-attempt transport data. The core imported-stage verifier proves signature, context, decrypted ADMIN operation and compiler-derived part; runtime obtains source policy/checkpoint/Owner/key/ring and ancestry from complete origin-bound replay. The packet is protected and durably journaled before any POST. Exact same-ID retries reprove it after restart; mismatched journal contents refuse.

For applied response loss, replay's exact signed command, commit hash, part and checkpoint resolve the saved packet without POST. For saved-before-send, attach imports the packet into a protected `ATTACHED_RESTRICTED` state without POST; ordinary action, install and format-transition selectors must refuse while read/status and the explicit exact-ID stage recovery remain available. Only `recover_pending_package_stage(attach_id, expected_command_id)` may POST the same canonical envelope while the authenticated current head, policy and epoch equal its pinned predecessor; fresh complete replay, not a 2xx response, proves acceptance and permits idempotent unlock to `ATTACHED`. A stale head, later cutover/ENFORCE rejection, transport uncertainty or missing signed result leaves the original packet protected with an actionable unresolved local status. Do not re-sign, regenerate ciphertext, drain a global queue, or label an HTTP rejection as a signed terminal outcome. A later explicit retain/disposition path is required if exact retry becomes impossible; do not silently abandon the packet. After protected attachment, native copies and history must support status/recovery without the old export paths. The old TS writer must be quiescent; the native root lock does not lock its files.

The first bounded positive gate may use genuine one-part PRIVATE wire-v3 STRUCTURED material with applied-loss and saved-before-send. Full completion still requires exact multipart prefix continuation and the orphan disposition, not only an interim refusal. PUBLIC/other intent-map migration remains separately required.
