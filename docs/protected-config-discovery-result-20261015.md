# Shared protected configuration discovery (T060)

Implemented and verified in native/compiled-local Linux scope. `load_config(path=None)` / `loadConfig(path?)` and `peerwork config resolve [PATH]` call one new native read-only resolver. Existing explicit constructors and CLI JSON-file paths are unchanged. The default-config Owner examples use the helper explicitly; no implicit identity/config provisioning was added.

Selection is explicit path > `PEERWORK_CONFIG` > OS location. Linux uses `$XDG_CONFIG_HOME/peerwork/config.json`, or `$HOME/.config/peerwork/config.json` only when XDG is unset; macOS uses `$HOME/Library/Application Support/peerwork/config.json`; Windows uses `%APPDATA%/peerwork/config.json`. Empty/relative OS roots and every selected-file failure stop without fallback. Input is exactly `origin` and `state_dir`, with unknown/duplicate fields rejected. Output is those two fields (Node maps `stateDir`). Relative state resolves against the config parent; parent traversal is refused. README and Agent entry document the exact selection/schema and idiomatic use.

The existing protected-file reader supplies bounded 16 KiB, regular-file, ownership/permissions, hardlink/symlink and canonical-parent checks. A new read-only directory check reuses the existing private-parent validator for state paths; missing state is allowed only under an existing protected parent. HTTPS validation matches the transport's origin predicate (no credentials, non-root path, query or fragment); this helper has no loopback override. Existing explicitly opted-in loopback constructors remain available. Failures expose fixed `CONFIG_LOCATION/MISSING/UNSAFE/LIMIT/INVALID` codes/messages, without raw paths, config text or OS errors. No identity, lock, authority default, directory creation or network operation occurs in the resolver.
