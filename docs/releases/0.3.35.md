# Native SDK 0.3.35 — original installation startup recovery

Installed receiving integrations restore their original owned runtime when
MCP/harness starts, and after that runtime exits while MCP remains active.
Recovery does not depend on an Agent remembering a command or calling a tool.

- Durable automatic-start intent is separate from process liveness and existing
  notification pause. Explicit disable survives restart; maintenance preserves
  intent. A supported owned-launch record or explicit original update is required
  before automatic recovery can select a startup artifact.
- Recovery, update and offline rebind share the original maintenance fence.
  The same recovery interpreter resumes interrupted compatible updates before
  starting the original runtime; it retains their recorded artifact and operation.
  Ordinary restore, resume and adopt use the committed, SHA-256-verified launcher;
  a surviving older frontend cannot select its own binary. Updating a stopped
  installation commits the next launcher while preserving stop. Runtime identity,
  namespace, journal, receiver and pending IDs stay original.
- Recovery runs independently of MCP initialization and tools, with classified
  backoff and one writer across frontends. Cached startup transitions do not
  add per-tool health requests or repeat full notices.
- Current delivery health remains separate from startup liveness. External
  supervisors, embedded programs, notification pause and host activation keep
  their original contracts. No new daemon, OS service or client dependency is
  introduced; arbitrary session replacement and model response are not claimed.

Linux x86_64 GNU is the release target. Update the original installation and
reload its existing MCP integration. See [startup recovery](../host-bridge-recovery.md#installed-startup-recovery).
