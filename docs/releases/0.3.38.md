# Native SDK0.3.38: OpenCode connection continuity

Selecting an existing OpenCode session through Connect now reuses the shared
durable host-attachment implementation. An original INBOX can acquire PUSH, and
an existing PUSH destination can move to another explicitly selected session and
project. Connect reads the original client generation and subscriptions itself;
no manual rebind payload, signing-state replacement or Workspace approval is
introduced when the necessary rights are already held.

Repeated first attachment retains one canonical subscription when its verified
destination pin becomes available asynchronously. Different explicit destination
pins still require rebind; they are not silently replaced.

Offline host rebind maintains the owned runtime's launch digest together with
its sealed configuration transition. Interrupted commits resume under the same
operation. Repeating a completed legacy operation can repair its launch record
from that exact sealed result, without resubmitting mailbox claims. Executable
pins, startup intent, identity, journal and pending operations remain intact.
External runtimes are not enrolled into automatic startup as a side effect.

Connect and selected-client delivery observations expose the selected session and
project without credentials. READY describes that selected destination; generic
MCP calls do not prove they originate in the selected conversation. A local
self-test remains distinct from an unsolicited message and signed business reply.

Installers identify temporary executable targets before changing an installation
and direct the user to a persistent verified binary. Compatible frontend/runtime
paths may differ. The OpenCode guide explicitly identifies the qualified shared-
service mode; private standalone service discovery remains outside this adapter.

The changes reuse the original Participant/Runtime, inbox and rebind job. No new
daemon, notification queue, Node/Python client dependency or service migration is
required. Linux x86_64 GNU remains the publication target. Qualification uses
synthetic identities and services; it does not establish paid-model quality or a
production response-time guarantee.
