# Native SDK 0.3.43: original client and receiving recovery

Ordinary frontends attach to the durable original Peer client. A new opted-in
receiving activation can replace its predecessor for the selected original
source group. Opening another RPC connection or reading status does not replace
receiving, and the newest executable does not select a host conversation.

The runtime commits activation ownership for the complete coalesced source
group. Stale polling and final notification admission are refused. A superseded
frontend cannot reclaim ownership through automatic retry; the current activation
reconnects using its existing decision. Recent activation receipts are bounded,
while the durable generation continues to reject retired activations after their
receipts are reclaimed.

Destination changes continue through the existing sealed host rebind. Its fence
covers the complete affected receiving group, including interrupted recovery,
and preserves original UNKNOWN host attempts. Activation replacement does not
reset notification batches, retry backoff, pause or stop. The original identity,
keys, journal, inbox, operation namespace and pending IDs remain intact. Other
Peers, Spaces and independently bound conversations keep their own state.

Installed startup recovery first authenticates a healthy endpoint against the
original client binding, without requiring historical config, PID or launcher
records. Starting, stopping or transferring an owned runtime still requires
original ownership, configuration, artifact and single-writer checks. Pending
updates and maintenance barriers remain authoritative.

Upgrade the original resident runtime and frontend together. Compatible runtimes
advertise `presentation-activation-v1`. Use the existing host opt-in or selected
Connect flow; no manual activation IDs or new daemon are required. Legacy
frontends need their normal refresh or drain before replacement, and physical
host locks remain in force. See [activation recovery](../host-bridge-recovery.md#receiving-activation-replacement).

Linux x86_64 GNU only. No service schema change or Node/Python client runtime is
required. Current service authorization and genuine delegated ceilings remain
unchanged. This release does not claim arbitrary host-session control, actual
Peer adoption, model response or measured throughput/latency improvements.
