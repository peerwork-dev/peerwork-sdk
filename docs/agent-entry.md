# Agent entry for a local Peerwork SDK trial

Use this entry when an operator has already provided a local Peerwork CLI, a service origin, and a protected state directory. This is an experimental SDK trial, not a published download or a claim that every platform is supported. Keep the operator's identity, workspace and source choices explicit. If a required input is missing, report what is needed instead of searching private files or inventing an authority.

1. Find the operator-supplied `peerwork` executable (or use `command -v peerwork` if it is on `PATH`). Run that exact executable's `version` and `capabilities`. Current source builds also accept `help`, `--help` and `-h` for a usage map; an older local artifact may report `USAGE` for help. In that case, use the documented command surface for that artifact and report the missing help command. Do not infer installation, network access or platform support from the capability list.
2. Establish the actor and workspace before writing. `identity info IDENTITY_STATE_FILE` reads a native identity file, not a legacy source-state JSON file or the state directory itself. An Owner profile uses the native identity at its configured `state_dir/identity.state`; when the operator explicitly selected a protected legacy PEM, `identity import-legacy-owner-pem OWNER_CONFIG_JSON_FILE PROTECTED_PEM_FILE` imports it to that exact protected path. Generic `identity import-legacy-pem IDENTITY_STATE_FILE PROTECTED_PEM_FILE` creates a native identity at the specified file, which need not be the Owner profile's file. Use `identity create IDENTITY_STATE_FILE` only when a new identity is requested and the existing path has been checked. Identity CLI paths may be relative to the current directory, but their parent must remain protected and source files must pass the CLI's private-file checks. Use the configured origin and protected state root. For an already created or attached Owner workspace, `secure owner-read CONFIG_JSON_FILE WORKSPACE_ID` returns the selected workspace's verified read. A historical source needs its explicit inspection and attachment before ordinary Owner read can succeed; a local attachment or operation listing is a recovery aid, not signed service acceptance. Other configured profiles have `secure read` or `secure private-read` with explicit origin, state, identity and workspace arguments. Confirm the Owner, visibility, policy and current signed state before acting.
3. Select a protocol or package from an identified source. The public catalog CLI exposes `secure catalog-search CONFIG_JSON_FILE QUERY` and `secure catalog-inspect CONFIG_JSON_FILE LOWERCASE_DIGEST`; inspect the exact selected bundle and its digest before using its bytes as an install input. A caller-selected local source or historical Owner import requires its explicit protected files and expected identities; pass protected material to the supported CLI operation rather than dumping its contents into tool output. Do not scan for keys, guess file pairings or print private material. Read the selected protocol's available actions, grants and input shape before calling an action. If discovery, trust or a required grant is unavailable, report that limit rather than substitute an unrelated source.

   For historical Owner package-stage inspection, `INPUT_JSON_FILE` is an object with `workspace_id`, `protected_ts_state_path`, `protected_ts_intent_db_path`, `protected_owner_pkcs8_path`, `expected_owner_actor_id`, and `expected_owner_key_id`. The operator must identify those three protected source files and both Owner pins; the SDK does not select them by scanning. `secure owner-stage-multipart-inspect CONFIG_JSON_FILE INPUT_JSON_FILE MATERIAL_JSON_FILE` inspects a saved pending stage packet, while `secure owner-stage-multipart-orphan-inspect CONFIG_JSON_FILE INPUT_JSON_FILE MATERIAL_JSON_FILE` inspects a packetless multipart marker. Inspection omits `selected_pending_package_stage_command_id`, `selected_orphan_package_stage_command_id`, and `expected_ts_state_digest`. An explicit attach uses the matching `...-attach` verb with the same source input plus **one** inspected command ID in the corresponding `selected_*_command_id` field and that inspection's `ts_state_digest` as `expected_ts_state_digest`; pending and orphan selections cannot be combined. `MATERIAL_JSON_FILE` is the complete caller-selected package material supplied as a file to the CLI, never printed or placed in a command argument. An inspection status describes source/replay evidence, not attachment or installation acceptance; a restricted attachment still needs its named recovery and signed completion before its stage ID is usable for installation.
4. Recover existing work before creating a new operation. For an Owner profile, `secure owner-operations CONFIG_JSON_FILE`, `secure owner-attachments CONFIG_JSON_FILE`, and the operation-specific pending/list command shown by the installed CLI expose protected local IDs. For example, PUBLIC action work uses `secure owner-action-pending CONFIG_JSON_FILE WORKSPACE_ID`; ordinary action profiles use `secure action-pending CONFIG_JSON_FILE`. Reopen the same profile and inspect these results after a lost reply, cancellation or restart. Match the origin, actor, workspace and intended operation before choosing an ID. Do not submit an equivalent new action while the earlier outcome is uncertain.
5. Use the exact saved ID for status, reconciliation or retry. PUBLIC Owner actions use `secure owner-action-status CONFIG_JSON_FILE WORKSPACE_ID COMMAND_ID` and `secure owner-action-retry CONFIG_JSON_FILE WORKSPACE_ID COMMAND_ID`; ordinary action profiles use `secure action-status CONFIG_JSON_FILE COMMAND_ID` and `secure action-retry CONFIG_JSON_FILE COMMAND_ID`. Other operation-specific recovery verbs are in the installed CLI usage. A saved `PENDING` row, a successful HTTP response or a CLI process exit does not prove business acceptance. For an action, require `ACCEPTED` under verified signed replay and the expected effect or readback. For an installation, attachment, identity publication or grant, use that operation's documented signed terminal state and required readback; do not promote a local-only listed or prepared state to completion.
6. Keep waiting bounded. Check the saved ID and use the operation's named exact retry or continuation within the caller's time and step budget. Some valid installs and migrations need several signed continuation steps; follow their documented progress rather than stopping after an arbitrary single retry. If the budget ends while status remains `PENDING` or explicitly unresolved, hand off the actor/workspace scope, saved ID, observed status and the next named recovery action. Do not loop indefinitely, mint a replacement ID or call a different command merely to obtain a successful exit. Keep packets, signing keys, raw protected files and private content out of the handoff.

This guide describes participant behavior at the SDK boundary. It does not authorize an Agent to coordinate unrelated actors, publish packages, select private sources without an operator, or treat a scripted SDK test as evidence that an Agent followed these steps. A future public cold start still needs published artifacts, supported-platform evidence and an observed Agent workflow test; the present local trial depends on the operator's supplied installation and configuration.
