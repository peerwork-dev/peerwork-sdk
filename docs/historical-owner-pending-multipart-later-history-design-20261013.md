# Pending multipart stage after later signed history — bounded design

This is a source diagnosis and next test plan, not an importer change or actual gate. Base SDK is `86f25e7`; the current f828 legacy client is `f828b6c50a0a58d1e718af90f653b214adcc3328`. The accepted `74b599b` gate covers an index-1 pending packet in a source of at least three parts when latest signed history is exactly the packet's predecessor or that packet, with current policy unchanged. The original packet, selected TS-state digest, full material and authenticated prefix are bound before PREPARED, and the imported stage row remains attach-owned.

`verify_pending_multipart_package_stage` already locates the package base checkpoint and authenticates each earlier ADMIN part, verifies the original saved signed packet against full caller material, and recognizes its exact commit at `base + index + 1` even when the replay sequence is later. It nevertheless requires `replayed.replay().policy_hash() == historical_policy_hash`. `imported_multipart_steps` imports only the earlier prefix and original packet. `continue_stage_for_attach` considers a later operation at the next required part sequence a plan conflict, correctly preventing stale continuation, while a later **complete** signed source cannot be reconstructed from the currently imported steps alone. By contrast `verify_completed_package_stage` authenticates every historical part through the final checkpoint, allows later signed history, then independently checks current PRIVATE Owner, key and active structure. Thus the recoverable completed-history case and the stale incomplete-prefix case need separate paths.

For a saved index-1 packet already accepted in complete replay, inspect/attach should recognize full signed completion only after matching **every** remaining consecutive part against the same compiler proof and source checkpoint, exact command/part index/previous/policy/Owner, and the original packet's unchanged signed commit hash and ciphertext. Reconstruct later `StageStep`s only from those authenticated commit wires; canonical `{commit:...}` envelopes for historical accepted steps are native storage bytes, not their original HTTP serialization. Keep the originally saved TS packet bytes for index 1. Require the complete source verifier to reproduce all parts and the full source ID/hash. The imported stage ID and attach provenance stay stable; no POST, new command ID, re-signing or re-encryption is authorized. A later signed action or same-epoch signed ceiling-raise policy may follow the completed prefix; current Owner membership/signing key, current PRIVATE visibility, active structure and usable current keyring must be proved **separately** before unrestricted attachment. If the current Owner was revoked, policy became PUBLIC or current epoch key is unavailable, refuse authority despite historical package completion. A current policy mismatch alone does not invalidate a fully authenticated historical source.

The old completed stage **cannot** be used directly for a new install BEGIN after later history. We initially considered relaxing the native installer’s exact-end check, but f828 `workspace-secure-install.ts::validateStructureInstall` makes that a wire invariant: BEGIN’s signed snapshot source must be its immediate predecessor and have the same policy hash and sequence `package_source.source.sequence + parts.length`. `workspace-protocol-install-plan.ts::resolveProtocolInstall` also uses a historical `packageEnd` only to verify provenance, not to authorize a later BEGIN from that old source. Keep the current core/native installer refusal with no new commit. To use the material after a later action or ceiling raise, the authorized Owner explicitly stages the **same material as a new package source at the latest authenticated checkpoint**, with new stage command IDs; only that newly signed source may be installed and read back. The old imported stage and original packet remain intact. This is an explicit new staging operation, never a silent re-signing of unresolved historical work.

If the original packet is not in signed replay and current head is not its exact predecessor, **never POST** it. If the original packet is signed but the full source is incomplete and a later unrelated commit occupies the next expected part sequence, the old source cannot be continued in place without changing its signed source identity. Preserve the exact original packet/material/selection and give an actionable stale-unresolved disposition before an immutable PREPARED row where possible; do not claim the packet was rejected or absent merely from a latest vector. No automatic replan, rebasing or signature regeneration belongs to this recovery path. Any future explicit disposition must retain uncertainty and original provenance.

Smallest proposed genuine fixture: use f828 public `stagePackageMaterial` with the existing >=3-part PRIVATE v3 STRUCTURED material and its dropped-response index-1 hook; retain a byte-exact protected snapshot of the old-client state/PEM/intent source while the original still holds the pending marker and packet. Then on the same official client call public `retryPending()` and `stagePackageMaterial` with the same source/material so signed history completes all parts, followed by a supported wiki action. Select the frozen source snapshot for native import; the old client must be quiescent before import. A second case calls public `enableFormatTwo()` after full stage completion to produce a genuine same-Owner, same-epoch signed policy transition with a different current policy hash. Both cases must show exact historical packet/source proof, no new imported-stage commit, sourcegone reopen, old stage-ID install refusal/no commit, then explicit new stage with same material followed by authorized install and authenticated protocol/instance readback. A paired incomplete-prefix case advances the signed head with an unrelated authorized action after original acceptance but before remaining stage parts: require no attachment activation or new stage POST, with exact original packet retained for a future explicit handoff. The fixture setup passed independently; these importer outcomes are proposed and have not yet run. Avoid direct service DB edits, old-state rewriting, unsupported admin commits or a changed Owner/key fixture that cannot be authenticated.

Existing external TS-writer quiescence and source-selection pairing limits remain. This scripted service evidence, when run, would prove business migration behavior only; Agent workflow compliance requires separate observed instruction-following evidence. ENFORCE, changed epoch without source key, missing full material, partial stale disposition and other intent-map families remain required beyond this bounded tranche.
