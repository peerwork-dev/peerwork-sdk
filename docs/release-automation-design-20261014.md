# Offline release automation scope

Initial base9898c4f, reconciled with accepted925cd9b, preserves accepted SDK runtime and installed evidence; c5e artifacts remain immutable. This package owns version/build/package/release tooling, workflow and narrow tests/docs. It does not change verification/runtime semantics, support flags or claim unexecuted native platforms. No registry, GitHub write, tag creation, auth lookup or credential probe is performed during local validation.

Cargo workspace version becomes the single native/Python authority: core/runtime inherit it, and Python declares dynamic version so maturin reads the native Cargo version. A small stdlib release tool checks Node root/optional-platform versions and Cargo.lock workspace packages against that authority, updates only their version fields for an explicit local version command, and refuses drift/tag mismatch before build or staging. Platform packaging derives version/repository/license from its root metadata. Existing CI filenames and smoke checks use checked metadata instead of hardcoded0.0.1. This preserves explicit caller-selected release identity; no registry lookup silently chooses a version.

The same tool stages only explicitly supplied built artifacts into a fresh directory, verifies wheel/tarball package identity/version and expected platform metadata, renames per-target CLI archives to avoid basename collisions, and writes exact asset checksums, source/toolchain/build metadata, dependency SBOM and license inventory. Locked Cargo metadata and checksums describe source dependencies; pinned ICU source/data/license and bundled LLVM runtime/license are separate components. Runtime/build/OS external dependencies remain labeled rather than guessed. No private paths or environment dump enters release assets. Missing/unknown license or dependency material must be reported and block release staging rather than being silently omitted. Pure/offline negative tests cover stale versions, duplicate/colliding artifacts, wrong platform/package/version, tampered checksum, manifest substitution and license gaps.

Tag-driven staging invokes the existing target build matrix and emits immutable per-target verified release bundles. Release assembly checks the exact tag/source/run and finite target set, retains checksums/SBOM/licenses, and signs build/SBOM provenance through GitHub OIDC. Publishing jobs use explicit environments and official PyPI/npm trusted publishing with preconfigured package/workflow bindings; no embedded long-lived tokens or local auth probes. GitHub assets and registry jobs publish the already staged assets, without rebuilding or changing version. Actual publication and repository/environment/trusted-publisher configuration remain external prerequisites, separate from source correctness or this local gate. The workflow must not publish an incomplete target set or treat build-source declaration as platform acceptance.

Reproducibility compares two separately built artifact inventories by name, target, version and exact bytes and fails on missing/extra/different outputs. Two deterministic metadata/package fixtures test the comparator locally; this does not claim two complete native builds are already byte-identical. The release workflow contains an actual independent same-toolchain build comparison before publication; any nondeterministic compiler/archive difference remains a failed release gate, not normalized away into a pass.

Primary documentation checked2026-10-14: [Maturin dynamic metadata](https://www.maturin.rs/metadata.html) permits Cargo-derived version via project.dynamic; [GitHub artifact attestations](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations) describes OIDC build/SBOM signing; [PyPI trusted publishing](https://docs.pypi.org/trusted-publishers/using-a-publisher/) provides the official publish action without stored API keys; [npm trusted publishing](https://docs.npmjs.com/trusted-publishers/) requires a configured workflow/package binding and modern npm/Node. The workflow will keep registry trust/environment setup explicit and will not infer its existence from local source.

macOS release requires an explicit protected signing/notarization job and configured Developer ID/Apple notarization credentials. Unsigned reproducibility is checked first; timestamped signatures and notarization may change bytes and are not normalized into equality. The signing step must verify each final signature and accepted notarization, retain unsigned-input→signed-output hashes, and rebuild checksums/attestations for the final assets. Missing macOS prerequisites block the complete finite-target release; they do not silently exclude macOS. Deterministic staging uses SOURCE_DATE_EPOCH from the exact source commit, fixed archive paths/order/owners/modes, and path remapping for independent unsigned builds. Unknown bundled component licenses block staging; system libraries are labeled external, not invented as bundled artifacts. [Apple code signing guidance](https://developer.apple.com/library/archive/technotes/tn2206/_index.html) confirms executable bytes change when signed; actual macOS/Apple execution remains separate from offline script validation.
