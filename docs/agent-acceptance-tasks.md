**Status: NOT RUN; NOT FROZEN.** These are draft task templates, not trial evidence or approval to start a run. Freeze only after the public Python, Node, and CLI entrypoints and release artifacts satisfy the phase-4/5 gates, actual-service scripted behavior is verified, and the task/runtime/environment pins below are filled and reviewed. ## Task scenario and participant setup

Give each Agent the same public-entry envelope, with values pinned before a trial: public release guide URL and release version; workspace display name and public service origin; the name/description of the authorized profile it should select through the documented public flow; reviewer and task-owner display names; and the task scenario below. Do not include source checkout paths, artifact cache locations, internal service endpoints, commands, expected IDs, credentials, or recovery instructions in this envelope. Supply authorization through the supported profile mechanism, not by exposing secret material in the prompt.

Start each trial in an isolated consumer environment where the SDK is absent. Python and Node runtimes may be present as recorded environment prerequisites; the native CLI trial requires neither runtime. Before the Agent environment is created, an operator may verify that the pinned public release artifacts are available, but must not preinstall them into that environment. Measure installation from the public entry through successful import/invocation as an observable Agent stage.

Use one isolated workspace per trial. Before an Agent starts, the test operator provisions its assigned proposer identity, a distinct reviewer identity, and a task-owner identity only through supported public service APIs. The selected active protocol must permit proposal creation, independent adoption, and task creation. The reviewer is a separately operated human or Agent participant using its own assigned identity and the ordinary public workflow; its review/adoption is observable and is never scripted into existence or performed by the proposer. The workspace should contain enough legitimate context for the proposal to cite an existing public source. Configure one hidden, deterministic lost-response event on a write request through the test service proxy; keep all fault injection and fixture setup outside the Agent prompt. Do not grant an identity broader authority than this scenario requires. Record operator setup and participant source artifacts separately from the target Agent events.

Run each template against an equivalent fresh workspace and corresponding identities. The only interface difference is the public entrypoint named in the template. Do not expose source checkout paths, harness commands, expected IDs, internal endpoints, or recovery hints to the Agent. Follow the public release's own entry instructions and applicable workspace protocol. Do not retry the trial to obtain a pass; preserve the first attempt and record any later independent run separately.

Capture one record per Agent attempt, with business correctness and workflow compliance scored separately. Retain the first attempt, any timeout or tool/runtime failure, subsequent recovery, and final handoff as distinct events.

## Freeze and reporting gates

Before freezing these tasks, bind each template to a tested public release and its exact public entry instructions; verify the corresponding invocation with the SDK absent initially and the other language runtimes absent. Keep artifact-availability preflight outside each Agent environment. Complete equivalent actual-HTTP proposal/adoption/task and lost-response scenarios for all three interfaces, then independently read back the relevant public records/source links through the established browser acceptance gate. Pin target OS/architecture/runtime for each run and use a process supervisor that actually supports that target; the inventoried Agent supervisor is Linux-only and the prepared old TypeScript prompts are not suitable substitutes for these native public-entry tasks.

No task is frozen until role permissions, reviewer response timing, failure injection point, timeout budget, completion/handoff deadline, service/source, supported protocol and expected effect predicates are fixed from supported public APIs and reviewed without disclosing those predicates to the Agent. Operator setup, proxy behavior, and expected outputs belong in the sealed test plan, not the prompt. The prompt must not be augmented with in-run hints after launch.

Report synthetic test workspaces separately from consented or publicly evidenced external acquisition. Do not count synthetic installs or trial identities as external adoption, people, or repeat users. Missing telemetry or tool-call observation is unknown. Preserve first-attempt evidence even if an operator later restores service state or helps a subsequent independent run.
